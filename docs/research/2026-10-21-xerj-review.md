## 为何改了很多，体验变化仍小

1. **迭代重心偏离可见结果。** 此前多轮集中于 CPU、纹理上传、滤镜和诊断脚本；其中有必要修复，但用户最关心的图标、艺术感和可操作性没有形成完整交付。性能现在按最新判断收口。
2. **新画面仍接着旧输入。** `src/renderer/app/game-tick.ts` 隐藏普通菇的旧视图；`game.ts` 的 `mushroomHit` 却仍遍历这些旧视图，要求 `growth >= 1` 且 `view.hit()` 成功。旧视图的 `hit()` 会拒绝不可见对象。新画布里的普通蘑菇因而没有对应的直接点击路径。管理窗按钮可以绕过这一问题，不能代替桌面交互验收。
3. **画面变化受固定模板约束。** `mildew-surface.ts` 的三组菌落位置、三个根部和菇体尺寸固定；随机种子改变的是霉点细节。`opening.ts` 给全部图标相同的时间曲线。用户描述的整齐感有直接代码原因；不必等待新素材才能改变节奏和少量构图参数，但本项优先级仍低于图标与界面。
4. **界面只迁移了部分功能。** 新管理窗有三个页面，小铺仅渲染 PVZ 铲子；设置仅有快捷键。`ui-root.ts` 仍装配旧商城、设置和桌面 HUD。不能把三个页面的存在等同于管理能力与视觉语言已经统一。
5. **旧展示逻辑尚未清理。** 火山菇领域层不再爆炸，但 `mushroom-view.ts:setCondition` 仍按旧 `lavaSeconds` 画环形倒计时并整体缩放。采摘也存在管理命令、普通动作和特殊采摘控制器多条路径；特殊控制器需要核对铲子门槛。
6. **进度记录没有及时收口。** README 仍出现“开发暂停”、双击自动清洁等旧描述；交付文档的早期段落仍写 Shell 尚未接入，后面的补记才说明已接入。大量修改混在未交付工作区里，源码、旧包、预览和历史测试的边界不够直观。

## 下一轮：一份可比较的体验包

按顺序只设三个用户可观察的目标，不把所有剩余项同时展开。

| 顺序 | 实施重点 | 完成证据 |
| --- | --- | --- |
| 1 | 图标与操作闭环：核对原生图案、显示大小和布局；新菇画面与命中共用几何；普通菇嫩时也可摘；特殊采摘各入口一致；干燥、清洗、采摘给出可见反馈 | 真实尺寸前后对照；鼠标直接点中并完成三类操作；退出恢复；相关行为回归 |
| 2 | 独立窗口完整设计：以当前纸色和标志为基础，完成小铺、设置与必要状态，缩减重复 HUD；只呈现当前真实可用的内容 | 同一版本的桌边、小铺、设置截图和一次完整原生操作；任务栏图标在便携包中验证 |
| 3 | 打包交付：明确本轮变化与剩余缺口，给出一个确定版本/哈希的新便携包 | 一份新包、短录屏、三条变化说明；由用户评价改善是否明显 |

视觉开发先选文件夹、彩色应用图标、浅色文档三个代表对象，在真实显示尺寸上并排比较；不要先铺满全桌面再靠放大截图判断。样片基准不覆盖。每轮结束都要产生可直接观察的结果，不能只以类型检查和源码行数作为进度。

生长精修随后进行：保持柔和体积和连续伸柄展伞，增加稳定的根部选择、数量差异、少量尺寸差异与错峰回放；避免每帧重随机，也不靠扩大整个图标制造明显变化。增强霉斑辨识度时同步检查原图可读性和 55% 联合遮挡约束。

多屏/不同 DPI、文件变化同步、存档边界、异常恢复及最终视觉确认仍属于原 Goal 的剩余要求。采用分批收口顺序，不把这些事项删除或宣称通过。
